## Top findings (highest-impact, reclassified)

1. **[DEMONSTRATED DEFECT, new 2026-10-03 -- GPT report on `34acd9c`, independently reproduced by Claude]** The PIT gateway derives `pit_status`/`knowledge_time_status` correctly, but `get_corporate_actions_as_of()` (`pit/access.py:245-254`) and `get_data()` (`pit/access.py:308-322`) wrap the result in `PITCorporateAction` (`pit/access.py:145-149`), which embeds the **full, unfiltered raw `CorporateAction` row** alongside the derived status -- including `source_status` and `source_status_date`. Reproduced directly against the real code: an action with `available_at=2024-03-01`, `effective_date=2024-03-20`, `source_status=CANCELLED`, `source_status_date=2024-03-15`, queried at `as_of=2024-03-10` (after the action is announced-knowable, before its cancellation is knowable) correctly derives `pit_status=ANNOUNCED` -- but the SAME returned object's `.action.source_status` already reads `CANCELLED`, and `.action.source_status_date` already reads `2024-03-15`, both facts that shouldn't be knowable yet at this simulated moment. A downstream consumer that reads the embedded raw fields instead of (or in addition to) the official derived `pit_status` field sees the future outcome early. SS12's own text is explicit that "PIT correctness este impusă prin access layer" (PIT correctness is imposed BY the access layer) -- the access layer does impose it on the derived field, but not on the raw object it hands out alongside that field, which is exactly the "look-ahead leakage" SS11 says this architecture exists to prevent. `tests/test_09_pit_look_ahead.py` and `tests/test_13_knowledge_time_policy.py` only assert on the derived fields, never on the embedded raw object, so neither test -- nor any other in the suite -- could have caught this. Not yet demonstrated: whether any current downstream consumer code actually reads `.action.*` instead of `.pit_status`/`.knowledge_time_status` (none exists yet outside Spec #001 that's been checked for this), so no live P&L contamination is shown -- only that the gateway itself does not structurally prevent it. No fix applied this round.
2. **[DEMONSTRATED DEFECT, new 2026-10-03 -- GPT report on `34acd9c`, independently reproduced by Claude]** `ingestion.ensure_security()` (`model/ingestion.py:48-61`) calls `adapter.fetch_security_info(ticker)` to get a `RawSecurityInfo` with its own `source_security_id` field (the adapter's contractually-declared provider identifier, per `adapters/base.py:28-34` and SS18.2's "mapează identifiers"), then **discards it**: `repo.insert_security_master(...)` is called with `source_security_id=ticker` hardcoded (`model/ingestion.py:59`), never `info.source_security_id`. Reproduced directly: a fake adapter whose `fetch_security_info()` returns `source_security_id="provider-123"` for ticker `"ABC"` results in a persisted `security_master.source_security_id == "ABC"`, not `"provider-123"`; `repository.get_security_by_provider_id(conn, provider, "provider-123")` (the function SS3.1's "Provider IDs trebuie mapate către security_id" names) then returns `None` for the adapter's own real ID, and only succeeds by accident if queried with the ticker instead. **This is why the dead-code finding on `get_security_by_provider_id` (formerly Top Finding 5/6) understated the issue**: the function isn't just unused, the data it would need to work correctly is never stored in the first place. Currently invisible in practice because the one implemented adapter (`YFinanceAdapter.fetch_security_info`) itself hardcodes `source_security_id=ticker` (`adapters/yfinance_adapter.py:81`), so `info.source_security_id` always happens to equal `ticker` today -- the bug is in `ensure_security()`'s handling of the adapter contract, not reachable with the current adapter, but real for any future provider whose own identifier differs from its ticker (e.g. a numeric internal ID, CUSIP, or similar). No fix applied this round.
