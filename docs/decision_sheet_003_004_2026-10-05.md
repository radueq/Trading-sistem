  common support reports `None` for `mean_difference`/`median_

- **Review verdict (GPT, relayed by Radu): ACCEPTED, but incomplete --
  the decisive regression for PARTIAL (not just zero) support was
  missing.** The joint remediation design's own section 6 text (lines
  904-917) already states this precisely: for a profile with partial

  unavailable -- `mean_difference`, `median_difference`, `raw_p`,
  `mean_difference_ci`, AND `standardized_effect` (since its formula
  consumes `median_difference` and `baseline_iqr` directly) all become

  plain `DescriptiveStats` (`absolute_outcome`/`relative_outcome`, over

  stay populated regardless, since nothing about common-support
  requires narrowing what the signature's own raw outcomes report, only
  what gets compared against a baseline and tested for significance.
- **Decision.** (a) UNAVAILABLE, confirmed. Known limitation: a
  signature with partial population mismatch surfaces with a complete
  comparison blackout (no effect size, no p-value, no CI) in the
  Research Queue, not merely a flagged or weaker one -- its own
  descriptive stats remain visible, so it isn't invisible, just
  unranked on outcome-strength.
- **Verification needed (the previously-missing regression, now
  specified).** A fixture with PARTIAL (not zero) common support:
  assert `mean_difference`/`median_difference`/`raw_p`/
  `mean_difference_ci`/`standardized_effect` are ALL `None` together;
  assert the SAME profile's `absolute_outcome`/`relative_outcome`
  `DescriptiveStats` remain fully populated from its own full episode
  set; a SEPARATE fixture with zero common support confirming the same
  `None` set (the degenerate case this document already covers); an

  None` propagates into `evidence/queue.py`'s ranking without crashing

### A4. Permutation exchangeability -- CORRECTED (substantial)

- **Proposal (Claude).** Accept full exchangeability for V1; ship the
  weighted-permutation estimator's `raw_p`/`adjusted_p` through the
  existing pipeline unchanged; flag the unquantified risk to Radu for
  his own awareness when judging a result.
- **Review verdict (GPT, relayed by Radu): CORRECTED -- accepting the
  estimator's MECHANICS is not the same as approving its OUTPUT as
  validated inferential evidence, and that distinction was not
  enforced anywhere in the design.** The absence of a block-permutation
  design does not validate value-level permutation; BH correction
  adjusts for multiple comparisons, it does not repair an invalid
  p-value's own underlying validity. Confirmed this round, by reading
  `src/hypothesis/evidence/queue.py` lines 83-88: `compute_review_
  priority()` uses `packet.primary_adjusted_p` as the PRIMARY ranking
  key (`p_key`) -- an unverified p-value does not merely get reported,
  it actively moves a signature up or down the Research Queue today's
  design would produce. Required: results from this permutation
  mechanism may serve a DIAGNOSTIC role; they must not be able to
  automatically satisfy significance criteria or drive promotion/
  ranking as if validated, until a method adequate to the data's actual
  dependence structure is justified and verified.
- **Decision.** Adopt the weighted-permutation estimator's MECHANICS
  (unchanged -- equal-weight case verified byte-identical to today's
  existing test). **New, required separation, specified now, before
  implementation:** `BaselineComparison` gains an explicit
  `exchangeability_status` field (modeled on the existing
  `standardized_effect_status` discipline), always set to
  `"UNVERIFIED"` for V1 -- applying uniformly to EVERY `raw_p`/
  `adjusted_p` this mechanism produces, at equal OR unequal weights,
  since the underlying risk (within-security serial correlation
  violating exchangeability) is not created by unequal weighting and is
  not resolved by it either; today's already-shipped equal-weight
  mechanism carries the identical, previously-unnamed risk. While
  `exchangeability_status == "UNVERIFIED"`, `evidence/queue.py`'s own
  `compute_review_priority()` MUST compute `p_key` as neutral (`float(
  "inf")`, the SAME fallback already used for a genuinely `None`
  `adjusted_p`) rather than using the actual p-value -- ranking falls
  back to `effect_key`/`support_key` only. `raw_p`/`adjusted_p`
  themselves are still computed, stored, and visible on `EvidencePacket`
  for a human reviewer's own diagnostic use; they are simply excluded
  from driving automated priority while unverified. BH's own multiple-
  testing correction continues to run unchanged -- this separation is
  about validity, not about disabling multiple-testing discipline.
- **Known limitation, stated without softening.** Nothing in this
  design yet defines what WOULD count as "a method adequate to the
  data's dependence structure" (block permutation remains undefined, as
  already named) -- `exchangeability_status` has exactly one value for
  V1 (`"UNVERIFIED"`); no path to a `"VERIFIED"` state is designed yet.
  This is intentionally conservative, not a placeholder for an
  unstated future mechanism.
- **Verification needed.** The exhaustive-enumeration regression,
  PRESERVED exactly, per Radu's own instruction: signature `[8]`;
  baseline rows `A=[0,2]` (2 rows), `B=[4]` (1 row), `k=2`; fixed
  per-row weights `[1/4, 1/4, 1/2]`; observed difference `8 - 2.5 =
  5.5`; all `4! = 24` orderings of the four pooled values across the
  four FIXED positions; two-sided, ties-included, gives EXACTLY `8/24 =
  1/3`. **This verifies the algorithm's own arithmetic, not
  exchangeability in real data -- stated explicitly so it is never
  read as the latter.** NEW: a test confirming `exchangeability_status
  == "UNVERIFIED"` on every profile this mechanism touches; a test
  confirming `compute_review_priority()` ranks a profile with a very
  small (falsely "significant"-looking) `adjusted_p` NO HIGHER than it
  would with `adjusted_p = None`, i.e. the unverified p-value cannot
  move it up the queue.

## E. Spec #004 Finding 16/GPT-G3 -- atomicity guarantee scope

### E1. Stated 3-condition/synchronous-only scope -- CORRECTED (limitation understated)

- **Proposal (Claude).** Accept the stated scope; described the
  concurrency/storage-failure gap as something that "needs
  re-examination" mainly in a FUTURE scenario (parallel execution, or a
  move off the in-memory dict).
- **Review verdict (GPT, relayed by Radu): CORRECTED -- the gap is not
  conditional on a future migration.** Any exception or failure outside
  the three named conditions (content mismatch; PREREGISTERED-content
  mismatch; variant content mismatch) can leave the registry in a
  partial state TODAY, under the CURRENT plain in-memory dict, with
  nothing about this mechanism preventing it -- the guarantee's
  narrowness is a present fact, not a risk that first appears after a
  storage-layer change.
- **Decision.** Accept the stated 3-condition/synchronous-only scope as
  the mechanism's actual, current guarantee -- no wider mechanism
  pursued now. The guarantee's boundary is restated precisely: it covers
  EXACTLY the three named conditions, under synchronous execution with
  no interleaved caller; nothing else is covered, in memory, today, not
  only after some future change.
- **Known limitation, restated without softening.** An exception outside
  the three named conditions (e.g. an unexpected error from a bug
  elsewhere in the call path) is NOT guaranteed to leave the registry
  in an all-or-nothing state RIGHT NOW -- this is a present gap in the
  CURRENT in-memory implementation, not a hypothetical one introduced by
  a later storage-layer migration. **Any implementation plan or
  acceptance criteria for this mechanism must name this EXACT scope --
  never describe it as a general all-or-nothing atomicity guarantee.**
- **Verification needed.** The three named regression cases under the

  synchronous-execution precondition; the acceptance criteria for this
  item (in the implementation plan) must quote this exact 3-condition

## J. Spec #003 S1 -- numeric validation (price finiteness/positivity)

### J1. Finite-and-positive price check -- PROPOSAL REJECTED, corrected to code enforcement

- **Proposal (Claude).** S1 handled as a documented trust boundary for
  V1, not enforced in code, on the premise that "no design exists
  because none has been attempted."
- **Review verdict (GPT, relayed by Radu): REJECTED -- the premise was
  false.** `docs/spec003_remediation_proposal_2026-10-04.md`'s own S1
  section (lines 463-481) already describes a concrete mechanism:
  `compute_forward_outcome()` divides by `entry_bar.split_adjusted_
  close` with no zero/finite guard today (`0.0` raises uncaught;
  `NaN`/negative/`inf` pass through as `VALID`); the proposed fix is a
  finite-and-positive check on both `entry_bar` and `exit_bar` prices
  before the division, routing to the ALREADY-AVAILABLE `INVALID_INPUT`
  status rather than raising or returning a nonsensical `VALID` result.
  Justifying "documented boundary" by "no design exists" was simply
  wrong -- a design existed in this project's own prior documentation
  and was not checked before writing the proposal.
- **Decision.** Adopt code enforcement, per GPT's decision: Evaluation
  explicitly verifies that the numeric prices used in the calculation
  are FINITE and STRICTLY POSITIVE. If not, it produces `INVALID_INPUT`
  -- no division performed, no `VALID` result produced. `None` cases
  stay handled distinctly, through the existing missing-data contract
  (B2's `DATA_GAP`/4a-4b handling), never folded into this check. The
  SAME rule applies to benchmark prices used for the relative-return
  side (the audit document's own row 19 names the identical gap for
  `benchmark.py`'s own date-alignment check, which today verifies only
  bar PRESENCE, not price finiteness). **S1's own classification
  (SUSPECTED, not yet a demonstrated contract violation) is NOT changed
  retroactively by this decision -- this is adopting the already-
  proposed protection as a technical decision now, not reopening or
  reclassifying the finding.**
- **Known limitation.** None identified for the check itself; the
  surrounding question of whose responsibility this SHOULD be (Evaluation
  defensively checking regardless of upstream guarantees, vs. trusting a
  QA/PIT boundary) is resolved in favor of Evaluation checking --
  consistent with this project's own repeated fail-closed pattern
  elsewhere in this registry (A1, B1, G1).
- **Verification needed.** Regressions for `0.0`, negative, `NaN`, and
  `+inf`/`-inf` at BOTH entry and exit prices, each asserting
  `INVALID_INPUT` rather than an exception or a nonsensical `VALID`
  result; the identical four-value regression set applied to the
  benchmark price used for the relative-return calculation.
