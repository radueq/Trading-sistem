## A. Spec #003 statistics

### A1. F3 common support -- (a) UNAVAILABLE

- **Decision.** When a signature/horizon profile's population and the
  baseline's population do not share full common support -- PARTIAL
  mismatch or ZERO common support alike -- `mean_difference`, `median_
  difference`, `raw_p`, `mean_difference_ci`, and `standardized_effect`
  ALL become `None` TOGETHER for that profile, never a partial subset
  of them. The signature's own plain `DescriptiveStats` (`absolute_
  outcome`/`relative_outcome`, over its FULL episode set) are NOT
  restricted -- they stay populated regardless, since nothing about
  common-support requires narrowing what the signature's own raw
  outcomes report, only what gets compared against a baseline and
  tested for significance. (This is `docs/joint_remediation_design_
  003_004_2026-10-04.md` section 6's own text, lines 904-917,
  confirmed correctly reflected here.)
- **Justification.** Consistent with this remediation's repeated
  fail-closed pattern (`CALENDAR_UNVERIFIED`, PREREGISTERED-only, G1):
  silence over a number that would need a caveat a reader might miss.
- **Known limitation.** A signature with partial population mismatch
  surfaces with a COMPLETE comparison blackout in the Research Queue
  (no effect size, no p-value, no CI), not a flagged or weaker one --
  its own descriptive stats remain visible, so it isn't invisible,
  just unranked on outcome-strength.
- **Verification needed.** A fixture with PARTIAL (not zero) common
  support: assert `mean_difference`/`median_difference`/`raw_p`/
  `mean_difference_ci`/`standardized_effect` are ALL `None` together;
  the SAME profile's `absolute_outcome`/`relative_outcome`
  `DescriptiveStats` remain fully populated; a SEPARATE fixture with
  ZERO common support confirming the identical `None` set; an
  end-to-end check that `EvidencePacket.primary_standardized_effect is
  None` propagates into `evidence/queue.py`'s ranking without crashing
  or substituting a different value.

### A3. One pooled weighted baseline distribution -- replaces Level 1 entirely

- **Correction, per GPT's own explicit decision, relayed by Radu: the
  prior entry wrongly deferred the relationship between `baseline_
  median` and the distribution feeding `baseline_iqr` as an "open
  consistency question." It is not open -- GPT decided it.** Revision
  5 kept `stratified_baseline_point_estimate()` "explicitly UNCHANGED,"
  but that function's own signature --
  `stratified_baseline_point_estimate(baseline_dated_values: list[
  tuple[str, float]], weights_by_bin, bins, stat)` -- receives only
  `(date, value)` pairs, with NO security identity. It CANNOT implement
  per-security weighting at all, regardless of what `stat` is passed in,
  because it has nothing to weight BY. Keeping it unchanged does not
  "defer" F4+F5 for the reported baseline mean/median -- it fails to
  deliver F4+F5 for them, silently. **Confirmed by direct computation
  this round (not hand arithmetic -- run via Python, exact fractions):**
  one bin, security A with values `[0, 2]` (2 rows), security B with
  value `[4]` (1 row), `k=2` securities, per-security weights `W_b/(k*
  n_i)` give row weights `[1/4, 1/4, 1/2]`. Today's actual code
  (`_pystats.median`/plain mean over the raw row LIST, ignoring
  security identity) gives row-mean `2.0`. The AGREED per-security
  weighting gives weighted mean `5/2 = 2.5`. **Different answers --
  `stratified_baseline_point_estimate()`'s own current behavior does
  NOT deliver the agreed weighting for the reported baseline mean,
  confirmed, not merely argued.**
- **Decision (GPT's, not Claude's synthesis this time -- stated
  precisely as such).** ONE pooled weighted baseline distribution,
  built from EVERY eligible row across all bins, each row carrying its
  own per-security weight `W_b/(k_b*n_i,b)` (the ALREADY-AGREED F4+F5
  formula, bin-aware: `b` = the row's own bin, `k_b`/`n_i,b` = distinct-
  security-count/this-security's-row-count WITHIN that bin), feeds ALL
  THREE of:
  - `baseline_mean`: the weighted mean of that one pooled distribution.
  - `baseline_median`: the weighted quantile Q(0.5) of that SAME pooled
    distribution, under the midpoint convention with mandatory
    tie-aggregation (section 4.2).
  - `baseline_iqr`: Q(0.75) - Q(0.25) of that SAME pooled distribution,
    same convention.
  **This REPLACES `stratified_baseline_point_estimate()`'s own two-level
  Level-1 mechanism (per-bin PLAIN stat, then bin-weighted-average) --
  it is not left standing alongside the new mechanism.** The function's
  own signature must change to accept security identity (or
  pre-computed per-row weights) to make this possible at all.
- **Verified by direct computation, the SAME fixture, exact fractions
  (`python3`, `fractions.Fraction`, this round):** pooled distribution
  `{(0, 1/4), (2, 1/4), (4, 1/2)}` gives weighted mean `5/2 = 2.5`,
  weighted median `8/3 ~= 2.667`, Q1 `= 1`, Q3 `= 4`, IQR `= 3` -- all
  THREE statistics drawn from the identical pooled set, all three
  numerically DIFFERENT from today's unweighted row computation
  (mean `2.0`, median `2.0`).
- **Explicit non-scope, unchanged from before.** This does NOT touch the
  signature's own existing, UNWEIGHTED `DescriptiveStats.q10/q25/q75/
  q90` (`describe()`, `src/evaluation/statistics/descriptive.py` line
  25, `np.quantile`) -- a separate, untouched code path, never the
  baseline's. The `session_mass` diagnostic (A2) stays purely
  descriptive, never consumed by this mechanism either.
- **Consequence for A4 (permutation) and bootstrap -- stated explicitly,
  per GPT's own instruction ("the permutation and bootstrap estimators
  must correspond to the reported mean, per the already-established
  design"):** the permutation test's own "observed difference" (e.g.
  `signature_mean_relative - baseline_mean`) and the bootstrap's own
  per-replicate statistic (already specified in section 6, carried
  forward in Stage 4) MUST draw from this SAME corrected, pooled,
  per-security-weighted baseline computation -- never the old row-mean.
  There is one baseline-estimation mechanism now, consumed uniformly by
  the point estimate, the permutation test, and the bootstrap replicate
  statistic -- not three independent approximations of "the baseline."
- **Downstream #004 effect, chain confirmed by reading the code.**
  `baseline_mean`/`baseline_median` feed `mean_difference`/`median_
  difference`; `baseline_iqr` feeds `standardized_effect` via
  `_standardized_effect(median_difference, baseline_iqr)`
  (`src/evaluation/engine.py` line 217) -> `EvidencePacket.primary_
  standardized_effect`/`primary_baseline_median` (`packet.py` lines
  163-164) -> `evidence/queue.py`'s own ranking (`effect_key`, line 86).
  All three statistics' new, corrected values reach #004 through this
  one chain.
- **Known limitation.** Midpoint does not reproduce `statistics.
  quantiles(..., method="inclusive")` in the general case; this
  divergence now flows into `baseline_mean`/`baseline_median`/
  `baseline_iqr` together, and therefore into `median_difference`/
  `standardized_effect`'s actual numeric values.
- **Verification needed.** The numeric regression above (row-mean `2.0`
  vs. weighted mean `2.5`; row-median `2.0` vs. weighted median `8/3`),
  locked as an exact-fraction test, not a float approximation; a
  SEPARATE assertion that `baseline_median` and `baseline_iqr`'s own
  `Q1`/`Q3` are computed from the IDENTICAL pooled weighted set (same
  row weights, same aggregation) -- not two independently-constructed
  distributions that happen to agree by coincidence; weight-rescaling
  invariance (>= 3 scale factors), the tie/weight-permutation matrix,
  and zero/negative/non-finite handling, all applied to this one
  mechanism; an end-to-end trace confirming the corrected `mean_
  difference`/`standardized_effect` reach `EvidencePacket`/`evidence/
  queue.py`'s own `effect_key`.

### A4. Permutation mechanics accepted; `exchangeability_status` is a cross-module design, specified in full

  existing `stratified_permutation_p_value()` test). **This does NOT,
  by itself, make the resulting `raw_p`/`adjusted_p` validated
  inferential evidence** -- the lack of a block-permutation design does
  not validate value-level permutation, and BH correction adjusts for
  multiple comparisons, it does not repair an invalid p-value's own
  underlying validity.
- **Decision -- the field.** `BaselineComparison` gains
  `exchangeability_status: str`, with exactly ONE legal value for V1:
  `"UNVERIFIED"`. This is hard-coded by whatever function builds
  `BaselineComparison` -- **it is never exposed as a caller-supplied
  constructor argument anywhere in the call chain, so no caller can
  activate inferential use merely by passing the text `"VERIFIED"`.**

  implemented in V1; there is no mechanism to reach it. It applies
  uniformly to EVERY `raw_p`/`adjusted_p` this mechanism produces, at
  equal OR unequal weights -- the underlying risk (within-security
  serial correlation violating exchangeability) is not created by
  unequal weighting and is not resolved by it; today's already-shipped

  named uniformly rather than selectively.
