## A. Spec #003 statistics

### A1. F3 common support -- DECIDED: (a) UNAVAILABLE for mismatched populations

- **Chosen solution.** When a signature/horizon profile's own
  population and the baseline's population do not share full common
  support, `BaselineComparison`'s `mean_difference`/`median_difference`/
  `raw_p`/CI fields report `None` for that profile entirely. No
  restricted-to-common-support substitute is computed.
- **Justification.** Consistent with this remediation's own repeated
  pattern of preferring a clean `None`/fail-closed result over a number
  that could carry a subtler bias: restricting a comparison to the
  overlapping support, even with an honest exclusion count, still risks
  the excluded episodes being systematically different from the
  included ones, which a bare exclusion count does not correct for.
  This project has made the same call elsewhere (`CALENDAR_UNVERIFIED`,
  the PREREGISTERED-only gate, G1 below) -- silence over a number that
  needs a caveat a reader might miss.
- **Known limitation.** Fewer profiles get ANY effect-size number: a
  signature whose population partially mismatches the baseline shows no
  `standardized_effect` at all, not a weaker or qualified one.
  Confirmed by reading the call chain (`src/evaluation/engine.py` line
  217; `src/hypothesis/evidence/packet.py` lines 163-165;
  `src/hypothesis/evidence/queue.py` line 84): this is the exact value
  `EvidencePacket.primary_standardized_effect` carries into the
  Research Queue's own ranking -- a signature landing here gets no rank
  signal from this field at all, rather than a flagged, lower-confidence
  one.
- **Verification needed.** A test asserting a profile with ZERO common
  support returns `None` for `mean_difference`/`median_difference`/
  `standardized_effect`/`raw_p`/`adjusted_p`; a test asserting a profile
  with FULL common support is unaffected by this choice; an end-to-end
  test confirming `EvidencePacket.primary_standardized_effect is None`
  propagates correctly into `evidence/queue.py`'s own ranking (no
  crash, no silent substitution of a different value).

### A2. Session-level weighting -- DECIDED: diagnostic-only, adopted now

- **Chosen solution.** Report a WEIGHTED `session_mass` diagnostic
  (summing per-security row weights per session, never a raw
  `Counter`) alongside existing output. The per-security formula's own
  equal-weight property is left untouched; `baseline_mean`/
  `baseline_median` and the signature's own descriptive stats do not
  change.
- **Justification.** Building a real session-level correction now
  would be speculative engineering against a problem not yet shown to
  be material for any actual signature; the diagnostic gives a cheap,
  verifiable way to detect whether the concern (SS74C's own concern
  about session-concentration dominance) is real before investing in a
  correction for it.
- **Known limitation.** If a signature's episodes concentrate heavily
  in a small number of sessions, the comparison against the baseline
  does not correct for that concentration -- it is only visible via the
  diagnostic, which must be checked explicitly.
- **Effect worth your attention (flagged, not a request to choose a
  mechanism).** Before relying on a FORMAL_DEVELOPMENT result for a
  capital decision, check the `session_mass` diagnostic for
  concentration on that signature. If it looks material, that's worth
  raising with us for a real correction -- this is exactly the kind of
  "challenge the direction" moment your own message named, not a design
  choice we're asking you to make.
- **Verification needed.** A regression confirming
  `stratified_baseline_point_estimate()`'s own output is byte-identical
  before/after the diagnostic is added; a test reproducing the 1-
  security/2-session vs. 9-security/1-session 5%/95% split via the
  WEIGHTED `session_mass` diagnostic (a raw `Counter` would wrongly
  report ~9%/~91%, which this test must regression-lock as the WRONG
  answer).

### A3. Weighted-quantile convention -- DECIDED: midpoint, adopted

- **Chosen solution.** Midpoint rule for weighted quantiles, with
  MANDATORY tie-aggregation, for `DescriptiveStats.q10/q25/q75/q90`.
- **Justification.** GPT's own recommendation; scale-invariant and
  simpler than the `R_i` alternative. Verified this round, by grepping
  `src/hypothesis/` for `q10`/`q25`/`q75`/`q90`: no match -- no #004
  code path reads these fields today, so this choice carries zero
  current #004-visible consequence regardless of which convention wins.
- **Known limitation.** Midpoint does not reproduce `statistics.
  quantiles(..., method="inclusive")` in the general case, including on
  some tie-free inputs -- a documented, accepted divergence from the
  stdlib convention. Relevant only if this project's own quantile
  output is ever compared directly against a `statistics.quantiles`
  reference computation elsewhere.
- **Verification needed.** Weight-rescaling invariance across >= 3
  scale factors; the full regression matrix section 4 already specifies
  (tie/weight permutation cases, zero-weight exclusion, negative/non-
  finite hard-fail, single-distinct-value input, empty-input `None`).

### A4. Permutation exchangeability -- DECIDED: accepted for V1

- **Chosen solution.** Ship the value-level weighted-permutation
  estimator now. The equal-weight case is verified byte-identical to
  today's existing plain-mean `stratified_permutation_p_value()` test.
- **Justification.** Block permutation has never been given a precise
  definition anywhere in this project -- pursuing it now would be
  open-ended design work with no demonstrated urgency; the accepted
  estimator is a real, verified improvement over today's unweighted
  mechanism regardless.
- **Known limitation, stated without softening.** Accepting the full-
  exchangeability assumption does NOT demonstrate that the resulting
  p-values are valid under within-security serial correlation -- this
  is an explicitly accepted, UNQUANTIFIED statistical risk, not a
  validated one.
- **Effect worth your attention.** Any `raw_p`/`adjusted_p` this
  mechanism produces carries this unquantified risk. For a signature
  whose episodes are not plausibly independent across time within the
  same security (overlapping or closely-spaced entries), the reported
  p-value is weaker evidence than it would be under genuine
  exchangeability -- worth keeping in mind when judging a final result,
  consistent with your own standard that the result is the proof.
- **Verification needed.** The consolidated regression list already
  in section 5/12 (equal-weight-byte-identical check against the
  existing test suite); every EXISTING test currently covering
  `stratified_permutation_p_value()` re-run and confirmed to still pass
  under equal weights.

### B2. Data-gap status naming -- DECIDED: one shared `DATA_GAP` status

- **Chosen solution.** A single new `OutcomeStatus.DATA_GAP` value

- **Known limitation.** A reader of `OutcomeStatus` alone cannot tell

## C. Spec #004 active configuration

### C1. Mandatory live re-read at gate time -- DECIDED: design (b), adopted

- **Chosen solution.** At `preregister_hypothesis()` gate time,
  `load_config()` is re-read fresh and its version compared against the
  approval-time pinned snapshot's own version; a mismatch is a hard
  gate failure.
- **Justification.** Matches the stronger freshness/currency guarantee
  this document has targeted since revision 10: that the approved
  config must ALSO still be the currently active one at registration
  time, not merely the one the human saw at approval time.
- **Known limitation.** Adds one more hard-failure mode to the gate (a
  live `load_config()` call that can now fail preregistration purely on
  a version mismatch) -- a new way for the gate to reject a call that
  design (a) would have allowed through.
- **Verification needed.** A test where the approved snapshot's version
  still matches the live re-read (gate proceeds); a test where the live
  config changed between approval and gate time (hard gate failure, per
  section 7's own regression list); confirmation that the SUBSEQUENT
  operation uses the PINNED snapshot, not a second, independently
  re-loaded object.

## D. Spec #004 Finding 14 -- gate-time revalidation

### D1. Option (i), live re-validate -- DECIDED, explicitly tied to C1

- **Chosen solution.** `preregister_hypothesis()` re-runs `validate_
  proposal()` live on the current `proposal` argument, against the
  config snapshot REGISTERED AND FROZEN for this operation (section 7's
  `RegisteredConfigVersion` mechanism) -- the SAME snapshot C1 governs,
  never a separately-loaded one. Under C1's adopted design (b), this
  means: the mandatory re-read first confirms the live config version
  still matches the approved snapshot, and ONLY THEN does validation
  run against that one pinned snapshot. This never authorizes
  substituting a different config than the one originally approved --
  it only decides whether a cached validation result may be trusted, or
  must be recomputed, against that single registered snapshot.
- **Justification.** GPT's own explicit recommendation; removes the
  cached-validation trust boundary entirely, so option (ii)'s narrative-
  field gap (`facts_from_evidence`/`interpretation`, excluded from the
  narrower economic fingerprint) cannot arise by construction, since
  live validation always re-reads every field `validate_proposal()`
  has ever read.
- **Known limitation.** Re-runs `validate_proposal()` on every
  preregistration attempt -- a small, bounded performance cost versus
  option (ii)'s cached-result shortcut. A cost tradeoff, not a
  correctness gap.
- **Verification needed.** A test confirming the gate recomputes
  validation on the live `proposal` rather than trusting any cached
  `ProposalValidationResult`; a test that a stale/altered
  `facts_from_evidence`/`interpretation` is caught (guaranteed by
  construction once live re-validation is adopted, but still worth a
  concrete regression).

## E. Spec #004 Finding 16/GPT-G3 -- atomicity guarantee scope

### E1. Stated 3-condition/synchronous-only scope -- DECIDED: accepted, not widened

- **Chosen solution.** The batch-internal simulated-sequential dry run
  guarantees no partial write under exactly THREE named conditions
  (content mismatch; PREREGISTERED-content mismatch; variant content
  mismatch), ONLY under synchronous execution with no write from
  another caller interleaved between the dry run and the real writes.
  No concurrency-safe or storage-failure-safe mechanism is pursued now.
- **Justification.** Nothing in this system currently calls
  `preregister_hypothesis()` from more than one caller concurrently
  against the same registry instance; building for a concurrency model
  that doesn't exist yet would be speculative, open-ended work.
- **Known limitation, stated precisely, not silently assumed away.**
  The guarantee does NOT hold under concurrent callers against the same
  registry instance, and does NOT cover a storage-layer failure if the
  registry is ever backed by something other than a plain in-memory
  dict.
- **Effect worth your attention.** If a future automation plan ever
  runs multiple preregistration processes in parallel, or moves the
  registry off a plain in-memory dict (e.g. a real database), this
  guarantee needs re-examination before being relied on -- flagged now
  so it isn't forgotten later, not something blocking today.
- **Verification needed.** The three named regression cases, each
  exercised under the simulated-sequential dry run; an explicit test/
  doc note stating the synchronous-execution precondition as the
  guarantee's exact boundary.

## G. Spec #004 Finding 1 -- evidentiary admission

### G1. Admission policy -- DECIDED: hard-reject EXPLORATORY-sourced evidence

- **Chosen solution.** `preregister_hypothesis()` hard-rejects any
  proposal whose `source_evidence.evaluation_mode != "FORMAL_
  DEVELOPMENT"`, enforced against the REAL `EvaluationRunRegistry`
  record the evidence actually traces to (via `check_provenance_
  matches_run()`), never a self-reported field alone.
- **Justification.** Symmetric with Finding 2's already-adopted
  treatment of `research_mode`; consistent with this remediation's own
  demonstrated fail-closed philosophy (A1, B1 above); EXPLORATORY
  evidence carries a materially higher false-discovery risk than a
  FORMAL_DEVELOPMENT run and warrants the same procedural treatment.
- **Known limitation, stated without overclaiming.** This enforces
  PROCEDURAL discipline only (pre-registration, BH correction) -- it
  does NOT, by itself, resolve whether a pattern was already informally
  noticed during the exploratory search. Its actual statistical benefit
  stays bounded until/unless a genuine confirmation protocol (G2) is
  defined.
- **Verification needed.** A test asserting rejection when
  `source_evidence.evaluation_mode == "EXPLORATORY"`; a separate test
  asserting rejection when `evaluation_mode` FALSELY claims `FORMAL_
  DEVELOPMENT` but the real `EvaluationRunRegistry` record shows
  `EXPLORATORY` (the mode-vs-registry cross-check).

### G2. Out-of-sample confirmation protocol -- future technical work, not yet designed

- **Status.** Whether and how to define a genuine confirmation protocol
  (e.g. requiring a FORMAL_DEVELOPMENT run to cover a held-out period
  the exploratory search never touched) is now GPT/Claude's own future
  design responsibility, not Radu's -- but it is NOT designed yet, and
  is named here as open future work, not decided today.
- **Effect worth your attention -- this ties directly to your own
  reserved category on capital risk, so it is named plainly rather than
  silently deferred.** Even with G1's hard-reject adopted, NO mechanism
  in this document yet confirms that a FORMAL_DEVELOPMENT signature's
  edge wasn't already informally noticed during exploration. Any
  capital-allocation decision based on FORMAL_DEVELOPMENT evidence
  today inherits this bounded, not-fully-confirmatory status -- worth
  weighing explicitly when you decide whether and how much capital a
  given strategy deserves, since that decision stays yours regardless
  of how this protocol eventually gets designed.
- **Verification needed.** None yet -- this is unscoped design work, to
  be sized and specified before it can be tested.

## I. Spec #003 S2 -- run-id scheme marker

### I1. `run_id_scheme_version` marker -- DECIDED: adopted, inside the hash preimage

- **Chosen solution.** A separate, literal `run_id_scheme_version`
  constant (e.g. `"v2"`), included INSIDE `build_run_id()`'s own
  fingerprint INPUT -- not merely recorded alongside the id in
  `EvaluationRunRegistry`'s provenance. Bumped by hand whenever
  `build_run_id()`'s own field set changes. Historical `evaluation_
  run_id`s under an older scheme are never reinterpreted.
- **Justification.** GPT's own correction (placement INSIDE, not
  beside, the hash) closes a real identifier-collision gap
  structurally: two runs under different schemes could otherwise
  collide on an identical id if every hashed field happened to match.
  Matches this project's own existing discipline for `OUTCOME_ENGINE_
  VERSION`/`HYPOTHESIS_ENGINE_VERSION`.
- **Known limitation.** Depends on a human remembering to bump the
  literal version string by hand whenever the fingerprint's own field
  set changes -- a manual-discipline dependency, not an automatically-
  enforced one, the same limitation the existing engine-version
  constants already carry.
- **Verification needed.** Two runs differing ONLY in `run_id_scheme_
  version` (identical config, identical every other hashed field)
  produce DIFFERENT `evaluation_run_id`s; a SEPARATE regression
  confirming two runs differing only in `horizons` (same scheme) also
  differ, showing config-content and scheme are independently captured.
