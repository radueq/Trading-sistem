## A. Methodological choices -- Spec #003 statistics

### A1. F3 common support: (a) UNAVAILABLE vs (b) RESTRICTED comparison

1. **Exact behavior proposed.** (a): when a signature/horizon profile's
   signature and baseline populations don't share full common support,
   `BaselineComparison`'s `mean_difference`/`raw_p`/CI fields report
   `None` for that profile entirely -- no partial-population substitute
   published. (b): where SUFFICIENT common support exists over only part
   of the population, compute a restricted comparison over that overlap,
   with an explicit exclusion count; a profile with NO common support at
   all still gets `None`, identical to (a)'s own degenerate case.
2. **Recommendation and author.** Claude's own recommendation, this
   document's synthesis -- NOT GPT-confirmed. Leans toward (a), grounded
   in this project's own established fail-closed pattern (`CALENDAR_
   UNVERIFIED`, the PREREGISTERED-only gate).
3. **Alternative and concrete consequence.** (a): fewer numbers reported,
   none population-mismatched. (b): more profiles get a number for
   PARTIALLY mismatched populations, each now qualified by an exclusion
   count a reader must interpret correctly -- not universal coverage,
   corrected this document already states.
4. **Domain affected / contractual change.** Spec #003's own
   `BaselineComparison`/statistics module (section 6). No change outside
   #003's own evaluation output shape -- does not touch #004 or #005.
5. **What Radu would approve at this stage.** Which of (a)/(b) becomes
   #003's shipped behavior for common-support handling.

### A2. Session-level weighting: diagnostic-only vs. a real second mechanism

1. **Exact behavior proposed.** A WEIGHTED `session_mass` diagnostic
   (summing per-security row weights per session, not a raw `Counter`)
   reported alongside existing output; the per-security formula's own
   equal-weight property stays untouched; no correction is applied.
2. **Recommendation and author.** Claude's own recommendation -- NOT
   GPT-confirmed. Diagnostic-only; pursue a real corrective mechanism
   only if the diagnostic later shows a real problem.
3. **Alternative and concrete consequence.** Building a real session-
   level correction NOW is explicitly NOT designed in this document --
   named only as something to pursue "if Radu judges the diagnostic an
   insufficient response to SS74C." Choosing this alternative today
   starts design work that doesn't exist yet, from either GPT or Claude.
4. **Domain affected / contractual change.** Spec #003's F4+F5 weighting
   (section 3). No #004/#005 impact.
5. **What Radu would approve at this stage.** Accepting the diagnostic-
   only response as sufficient for now, deferring any real mechanism
   until/unless the diagnostic shows a problem.

### A3. Weighted-quantile convention: midpoint vs. `R_i`

1. **Exact behavior proposed.** Midpoint rule for weighted quantiles,
   with MANDATORY tie-aggregation.
2. **Recommendation and author.** GPT's own recommendation, relayed by
   Radu.
3. **Alternative and concrete consequence.** `R_i` reproduces
   `statistics.quantiles(..., method="inclusive")` for tie-free, equal-
   weight input, but loses that property the moment any tie is
   aggregated (the `[0,0,10]` counterexample) -- neither convention is a
   strict superset of the other's guarantees; midpoint never reproduces
   `inclusive` even tie-free.
4. **Domain affected / contractual change.** Spec #003's quantile
   computation (section 4) -- `DescriptiveStats` q10/q25/q75/q90.
5. **What Radu would approve at this stage.** Adopting midpoint (with
   mandatory tie-aggregation) as the shipped convention.

### A4. Permutation exchangeability: accept for V1 vs. require block permutation first

1. **Exact behavior proposed.** Ship the value-level weighted-
   permutation estimator now (equal-weight case verified byte-identical
   to today's existing test), with a documented limitation: it assumes
   full exchangeability, not merely marginal equality, under within-
   security serial correlation.
2. **Recommendation and author.** Claude's own recommendation -- NOT
   GPT-confirmed.
3. **Alternative and concrete consequence.** Require block permutation
   first -- delays indefinitely, since block permutation has never been
   given a precise definition in any round of this document.
4. **Domain affected / contractual change.** Spec #003's `comparison.py`
   / permutation test (section 5).
5. **What Radu would approve at this stage.** Accepting the documented
   exchangeability limitation for V1, rather than blocking the whole
   mechanism on an undefined block-permutation design.

## B. Calendar choices (F1 / Spec #003-#005 boundary)

### B1. Calendar strictness threshold for #003

1. **Exact behavior proposed.** Require `OFFICIAL_VERIFIED` (via the new
   admission/registry contract, section 2) for FORMAL_DEVELOPMENT runs;
   synthetic calendars permitted only in declared tests.
2. **Recommendation and author.** GPT's own recommendation, relayed by
   Radu.
3. **Alternative and concrete consequence.** A looser tier -- #003 can
   proceed more often without a verified calendar, but its own
   calendar-based classification (section 1) then rests on a weaker
   verification guarantee than #005's own FORMAL-run requirement.
4. **Domain affected / contractual change.** #003 Evaluation only --
   does not touch #005's existing `require_verified_calendar_for_
   formal_run()` gate, which stays scoped to FORMAL (#005) runs exactly
   as today.
5. **What Radu would approve at this stage.** Which strictness tier
   #003 itself adopts.

### B2. Data-gap status naming (case 4a vs. 4b)

1. **Exact behavior proposed.** Whether "no bar at `T_target`" (4a) and
   "a bar exists but its price field is `None`" (4b, currently mapped to
   `INSUFFICIENT_FUTURE_DATA` even though its date isn't actually in the
   future) share ONE status name, or get TWO distinct names.
2. **Recommendation and author.** None on record. The document states
   this plainly as "Radu's own semantic naming call, unresolved, same as
   every prior round" -- no GPT or Claude recommendation attached.
3. **Alternative and concrete consequence.** One shared name: simpler
   output vocabulary, but conflates "not yet reached" with "data-quality
   gap at an already-reached date." Two distinct names: clearer
   semantics, but a new `OutcomeStatus` value to add and thread through
   downstream consumers.
4. **Domain affected / contractual change.** Spec #003's `OutcomeStatus`
   enum and `ForwardOutcome` consumers (section 1.3).
5. **What Radu would approve at this stage.** The naming scheme itself
   (one name vs. two, and if two, the new name's exact spelling).

### B3. Who performs admission and verification (operational choice)

1. **Exact behavior proposed.** Whether source ADMISSION (Step 0) and
   the session-comparison (Step 3) are performed by an automated check
   against a live feed, or by a named human against a published
   calendar.
2. **Recommendation and author.** None on record. "Radu's own
   operational choice, NOT resolved here -- if performed manually, that
   human IS the trust boundary, stated as such."
3. **Alternative and concrete consequence.** Automated: requires an
   actual approved-provider integration, not built, no commercial source
   evaluated. Manual: works today with no new integration, but the named
   human becomes the explicit, documented trust boundary for every
   admission.
4. **Domain affected / contractual change.** Data Foundation's own
   calendar-sourcing process (section 2, Steps 0/3) -- operational, not
   a code-contract change either way.
5. **What Radu would approve at this stage.** Which mode #003 actually
   uses once implemented, and, if manual, who the named operator is.

### B4. Calendar relocation (import-direction fix)

1. **Exact behavior proposed.** Move `TradingCalendar`/`build_trading_
   calendar()` out of `src/backtest/` into a neutral location (most
   naturally Data Foundation) importable by both `evaluation` and
   `backtest`, closing the reversed `evaluation -> backtest` dependency.
2. **Recommendation and author.** Recommended in the document's own
   text, but NOT explicitly attributed to GPT or to Claude there --
   flagged here rather than guessed, given this engagement's own
   repeated attribution corrections. Treated conservatively as this
   document's own synthesis unless Radu or GPT states otherwise.
3. **Alternative and concrete consequence.** Leave it in place: #003
   keeps importing from `backtest`, reversing this project's own
   verified one-way chain (Data Foundation -> Discovery -> Evaluation ->
   Hypothesis -> Backtest). Relocate: a pure move (confirmed --
   `build_trading_calendar()` sources/verifies nothing itself), every
   current `backtest` import site switches, plus a new architectural
   guard test (`evaluation` never imports `backtest`).
4. **Domain affected / contractual change.** Cross-cutting (#003 + #005
   import graph). A contractual change in import paths only -- no
   behavior change if chosen (regression-locked as pure-relocation).
5. **What Radu would approve at this stage.** Whether to relocate now,
   defer it, or leave the import direction as-is with a documented
   exception.

### B5. #005's own eventual adoption of the registry-based trust rule

1. **Exact behavior proposed.** Whether Spec #005's own `require_
   verified_calendar_for_formal_run()` should later switch from object-
   level self-consistency checks to the SAME identity+record resolution
   rule #003's design now uses (`VerifiedCalendarRegistry` +
   `CalendarVerificationRecord`).
2. **Recommendation and author.** None. Explicitly named as "a separate,
   NOT-decided question, named here, never assumed."
3. **Alternative and concrete consequence.** Adopting it: #005 gains the
   same source-authenticity guarantee #003's new design has, at the cost
   of migrating #005's own existing callers. Not adopting it: #005 keeps
   relying on object-level self-consistency alone -- the same limitation
   this round's design closes for #003.
4. **Domain affected / contractual change.** Spec #005 -- out of this
   round's scope; the #005/Batch 3 pause holds regardless of this
   answer.
5. **What Radu would approve at this stage.** Nothing -- named here for
   completeness only; no approval is requested while the #005/Batch 3
   pause holds.

## C. Active configuration -- Spec #004

### C1. Mandatory live re-read at gate time

1. **Exact behavior proposed (design (b)).** At `preregister_
   hypothesis()` gate time, `load_config()` is re-read fresh and its
   version compared against the approval-time pinned snapshot's own
   version; a mismatch is a hard gate failure.
2. **Recommendation and author.** This document's own standing
   recommendation (held since revision 10's predecessor rounds); GPT's
   own contribution this round was correcting the JUSTIFICATION (a
   freshness/currency requirement, not a claim that design (a) is
   unsafe), not originating the recommendation of (b) itself.
3. **Alternative and concrete consequence.** Design (a), no live
   re-read: uses exactly the config the human approved, correct with
   respect to that decision; it simply never catches a config changing
   between approval and registration, which (b) exists specifically to
   catch.
4. **Domain affected / contractual change.** Spec #004's preregistration
   gate (section 7) -- a real behavior difference (an added hard-failure
   mode) if (b) is adopted.
5. **What Radu would approve at this stage.** (a) vs. (b) as the gate's
   actual behavior.

## D. Gate-time revalidation -- Spec #004 Finding 14

### D1. Option (i) live re-validate vs. option (ii) cache + wider fingerprint

1. **Exact behavior proposed (option (i)).** `preregister_hypothesis()`
   re-runs `validate_proposal()` live on the current `proposal` argument
   at gate time, against whatever config versions are currently
   registered -- no cached validation result is trusted at all.
2. **Recommendation and author.** GPT's own explicit recommendation,
   relayed by Radu, this round.
3. **Alternative and concrete consequence (option (ii)).** Keep the
   cached `ProposalValidationResult`, but only once it carries a SECOND,
   WIDER "validation-input fingerprint" (covering `facts_from_evidence`/
   `interpretation` in addition to the narrower economic fields) plus a
   config-version staleness check -- now fully specified by this
   document, but still carries more machinery (two fingerprints, a
   staleness check) for the sake of avoiding one redundant validation
   call.
4. **Domain affected / contractual change.** Spec #004's Finding 14
   (approval-binding mechanism, section 10).
5. **What Radu would approve at this stage.** (i) vs. (ii) as the actual
   gate mechanism.

## E. Atomicity guarantee limit -- Spec #004 Finding 16/GPT-G3

### E1. Accept the stated 3-condition/synchronous-only scope, or require wider coverage

1. **Exact behavior proposed (as specified).** The batch-internal
   simulated-sequential dry run guarantees no partial write under
   exactly THREE named conditions (content mismatch; PREREGISTERED-
   content mismatch; variant content mismatch), and ONLY under
   synchronous execution with no write from another caller interleaved
   between the dry run and the real writes.
2. **Recommendation and author.** None on record -- the document poses
   this as an open question without proposing an answer either way.
3. **Alternative and concrete consequence.** Accept the stated scope:
   ships as designed, with the explicit, named limitation that
   concurrent execution or a storage-layer failure (if the registry is
   ever backed by something other than a plain in-memory dict) are
   outside this guarantee's reach. Require a wider guarantee: this is
   NOT a simple approval -- no design exists yet for concurrency-safe
   atomicity or storage-failure handling.
4. **Domain affected / contractual change.** Spec #004's preregistration
   write path (section 10).
5. **What Radu would approve at this stage.** Whether the stated
   3-condition/synchronous-only scope is accepted as the final
   guarantee, or whether wider coverage must be designed.

**Concrete gap flagged separately (per Radu's own instruction, not to be
conflated with an ordinary unapproved choice):** if Radu's answer to E1
is "wider guarantee required," that is a genuine, currently-undesigned
gap -- not a second existing option to pick, but new design work this
document has not yet produced and has not scoped or estimated.
